## M2-02 calendar contract

`LunarCalendar.from_csv` reads UTF-8 with optional BOM. It requires the five mapping columns from T09. `weekday` is optional and checked against the ISO weekday when present. `holiday` and additional metadata are optional. `lunar_leap` accepts the observed fixture tokens `true` and `false`. The Gregorian range runs from the first to last row with exactly one row per day. Lunar fields have numeric bounds and successive day values must advance within a month or roll from day 29 or 30 to day 1. The file supplies the mappings. The loader checks their internal consistency.

`to_lunar()` returns `(year, month, day, is_leap)`. `to_solar()` defaults to the regular month per SPEC §5.10. A caller passing `None` gets a result only when the tuple without a leap flag has one match. Missing and ambiguous requests raise `LunarLookupError`. An invalid CSV yields `W_CALENDAR_INVALID` with a diagnostic code, row and message in `run.json.split.calendar_diagnostic`. Missing files yield `W_CALENDAR_MISSING`. `calendar_ok` gates future lunar functionality. Gregorian processing can continue. M2-09 can construct the lookup index from `calendar_path` after checking status. M1 review and Lead review of the additive split fields are pending.

The historical baseline builds its reverse map with `r["lunar_leap"] == "true"`. That treats an unexpected token as false and lets duplicate keys replace earlier rows. It uses a configured path or a train-calendar fallback. M2-02 validates both keys and values and uses the active split's calendar. The baseline code corroborates the fixture encoding but supplies no official input snapshot.

## H7 temporal profile proposal (M2-05)

Review in dependency order. PR #1 (`m2/M2-04-resolver`) starts from the Phase 1 `main` at `0d1be04` and proposes `1.1.0`. PR #2 (`m2/rulebook-calendar`) stacks on PR #1 and proposes `1.2.0` for split diagnostics. PR #3 (`m2/rules-calendar-params`) stacks on PR #2 and proposes `1.3.0`. Its diff covers H7, which uses the M2-04 `same_period_alignment` field, yearless policy, and resolver tests.

The existing synchronous `ModelClient.complete()` handles the proposed `rule_profile` stage with template `rules.temporal.v1` and a JSON schema for `{value, span}` per field. A nonempty rulebook makes one call before dispatch, when extraction is enabled. The prompt receives the active split's NFC-normalized rulebook. Empty or missing text skips the call. The validator requires exact text after whitespace normalization and independently checks that a recognized complete clause supports the value. It rejects examples, conditional or unrecognized claims, conflicting supported statements, malformed candidates, and unsupported values. Recognition is deliberately conservative. Alternate wording without recognized evidence uses the generic field default. The fixed missing-year policy stays fixed. `prior_period_full=false` has no approved resolver behavior and falls back with `unsupported_runtime_value`.

`TemporalParams.provenance` uses the frozen `ParamProvenance` type. A missing entry represents the generic default, and `uses_generic()` preserves the generic-window flag whenever a field falls back. The runtime writes `run.json.split.temporal_params`, `split.temporal_diagnostics` and actual `split.calls`, including failed calls returned by the client. Calendar status and diagnostics are independent of profile extraction. Existing callers may still use `load_split(data_dir)` with generic defaults.

**CPU handoff.** `run(..., extract_temporal=True)` exercises the real bootstrap boundary with an injected `ModelClient`. The scripted integration test verifies exactly one request, request schema and rulebook source, recorded response, selective fallback, a Sunday-start resolved window, and continued Gregorian processing with a malformed calendar. This branch keeps the CLI on the existing generic path. PR #3 records the test and fixture results for the rebased branch.
